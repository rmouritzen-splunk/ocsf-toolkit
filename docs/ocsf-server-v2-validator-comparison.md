# Comparison with the OCSF Server v2 validator

OCSF Toolkit validation is based on the [OCSF Server v2 validator](https://schema.ocsf.io/api/v2/validate), which is exposed at `/api/v2/validate` and is distinct from the older validator at `/api/validate`. The Toolkit has since evolved independently and performs additional or more precise semantic checks, particularly for observables, inactive-profile attributes, nested constraints, and cross-field consistency.

This comparison records important user-visible differences reviewed on 2026-09-05. It is not an exhaustive parity matrix and does not promise continuing parity with later OCSF Server changes.

| Area | Additional or more precise OCSF Toolkit checks |
|---|---|
| Observables | Validates observable structure and type IDs, resolves every [observable path notation supported by the Toolkit](../README.md#observable-path-notation) against both the active schema and actual event, verifies scalar values and valueless object references, optionally enforces a preferred notation, and can report duplicate semantic identities. The v2 validator accepts simple paths and recognizes bracketed array segments during its schema-reference check, but it does not support root-relative JSONPath, distinguish path styles, verify the referenced event value or observable type ID, enforce preferred notation, or detect duplicates. |
| Profiles and object structure | Distinguishes a present attribute requiring an inactive profile from an unknown attribute, reports every profile that can enable it, and performs a bounded shallow value check. It also keeps ordinary objects closed when profile filtering leaves no active attributes; only a direct use of the generic `object` type is open-ended. |
| Values and constraints | The v2 validator accepts only decoded integers for `integer_t` and `long_t` and only decoded floating-point values for `float_t`. Its `long_t` range is signed 128-bit, which does not match the OCSF definition of an "8-byte long, signed integer value." OCSF `long_t` is therefore a signed 64-bit integer, exactly matching Go's `int64` and the Toolkit's signed 64-bit semantics; a value accepted by the v2 validator outside that range is not a valid OCSF `long_t`. OCSF Toolkit accepts a floating-point or decimal representation for an integral type when its value is finite, mathematically integral, and in range; for example, `1`, `1.0`, and `1e0` can all satisfy an integral type. It also accepts integral representations for `float_t` using `float64` conversion, treats null constraint paths as absent, resolves dotted constraint paths through nested objects, and measures `max_len` in Unicode code points. |
| Version and cross-field consistency | Distinguishes malformed semantic versions from valid earlier versions and reports overflow while deriving `type_uid = class_uid * 100 + activity_id`. The v2 validator implements the basic version ordering and `type_uid` equation but does not distinguish these failure cases. |
| Traversal completeness | Applies the recursive-object processing boundary and reports a mandatory processing issue when reaching the boundary makes validation incomplete, rather than silently presenting a partial validation as complete. |

OCSF Toolkit allows changing each validation check's level from its default to ignored, warning, or error. The OCSF Server v2 validator allows only enabling warnings for missing recommended attributes.

OCSF Toolkit also changes validation code names for consistency, including a common `validation_` prefix. Integrations that match the v2 validator's error or warning type strings must use the corresponding Toolkit code names; `ocsf-toolkit --list-validation-codes` lists every available code.
