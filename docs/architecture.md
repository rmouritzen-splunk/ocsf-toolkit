# Architecture

OCSF Toolkit provides a Go library and CLI for processing events with the lean compiled schema format produced by the OCSF Schema Compiler. The current event processors perform enrichment, enrichment removal, and validation.

## Public Packages

- `enrichment` defines the action values used to add, safely remove, force-remove, or leave enum siblings and observables unchanged.
- `eventschema` loads compiled schemas and provides the public processor configuration, pipeline-construction, and opaque processing-result APIs.
- `eventresult` defines the processor-specific result and diagnostic structs returned through `eventschema.ProcessingResult` accessors.
- `issue` defines typed, stable codes for non-fatal processing issues.
- `jsonio` reads JSON objects while preserving numbers as `json.Number` and rejecting trailing JSON values.
- `jsonish` defines `Map`, the common JSON-object type used by the public API.
- `pathstyle` defines the path-notation styles shared by observable enrichment and observable-name validation options.
- `schemaresult` defines nonfatal initialization issues returned while a compiled schema is loaded.
- `validation` defines typed, stable validation codes independently of their default and effective reporting levels.

Implementation details that library consumers do not need belong under `internal/`.

## Relationship To The Language-Neutral Model

The [event processing model](event-processing.md), [enrichment](enrichment.md), [enrichment removal](enrichment-removal.md), and [validation](validation.md) guides describe logical behavior that can be implemented with different encodings, data structures, and processing architectures. This repository is one concrete implementation of that behavior.

The public Go API accepts events as `jsonish.Map`, an alias for `map[string]any`. Nested maps, arrays or slices, and scalar values form the logical OCSF event tree. This generic representation makes one pipeline reusable across every OCSF class without generating Go types. `internal/eventvalue` centralizes null-aware attribute and dotted-path access, signed and floating-point conversion, scalar string conversion, OCSF-oriented type descriptions, and allocation-free indexed views over Go slices and fixed arrays, so callers can retain useful typed containers without duplicating representation mechanics across processors. Defined container types are accepted because they do not change their elements' logical values. Defined element types remain unsupported so array elements follow the same exact value-type contract as scalar attributes; aliases remain identical to their aliased types. The `jsonio` helpers decode JSON into the supported generic representation while preserving numbers as `json.Number`; JSON decoding is an input adapter rather than part of the processing algorithm.

The current public API does not directly traverse caller-defined structs, Java or Python classes, Parquet rows, or other concrete representations. A system using those forms can adapt them to `jsonish.Map`, construct an equivalent output map, or implement the language-neutral rules directly against its own field-access mechanisms. Equivalent implementations do not need to reproduce this repository's Go types or visitor design.

`internal/processing` owns the processing engine. One schema-guided walk supplies class, object, attribute, and completion callbacks to its configured processors. It consumes class and profile scope resolved by `internal/schema`, then centralizes null handling, profile-filtered attribute traversal, array traversal, and object recursion while leaving mutation and validation rules in their respective processors. `internal/observable` owns observable analysis, collection operations, and the diagnostics derived from analysis failures; internal processors decide whether those diagnostics become processing issues or validation findings. Immutable schema and pipeline data hold reusable work outside the event loop; a per-event context holds only event-specific state and results. Mutating processors run in configured order, and validation runs last. Enrichment removal and validation each analyze observables against the event state on which that processor operates, so validation always evaluates the final event.

This is an implementation choice, not an interoperability requirement. Another implementation could use generated validators, separate passes, columnar expressions, immutable record projections, or concrete class methods and still satisfy the documented behavior.

## Compiled Schema

`eventschema.Load` delegates compiled-schema decoding, normalization, indexing, and schema-scoped event queries to `internal/schema`. It accepts compiler format version 1 and expects the default lean output from `ocsf-schema-compiler`, not browser-mode output or the uncompiled schema repository format. Each load function returns the schema, any nonfatal schema initialization issues, and a fatal error. Within the internal package, `schema.Definition` is the decoded compiler document and `schema.Compiled` is its normalized, indexed representation used by processing. The compiled representation resolves event classes, extracts active profile scope, applies profile-aware attribute filtering, follows type inheritance, and calculates expected `type_uid` values. The public `eventschema.Schema` owns an `internal/processing.PipelineFactory`, which retains the compiled schema and processor-specific lazy caches without an intermediate public facade or duplicate compiled-schema pointer.

The compiler has already resolved includes, inheritance, patches, dictionary attribute details, and profile-expanded attributes. The loader treats compiled class and object attributes as authoritative rather than reconstructing the uncompiled schema. Optional dictionary sections are normalized so lean schemas can omit them safely. The compiled schema version is required and is parsed by `internal/semver` according to Semantic Versioning 2.0.0, including prerelease precedence and build metadata.

Byte-slice schema loading unmarshals directly from caller-provided data without copying or retaining it. File-based loading reads the known file size into one byte slice and uses the same decoding path, avoiding the additional full-schema buffer required by a streaming decoder for a single top-level value. Reader-based loading decodes directly from the source without consulting optional size methods; the decoder grows its internal buffer only in response to bytes read. Both decoding paths share schema normalization and indexing after decoding. The internal decoded representation retains only fields used by event processing. Compiler-facing `compile_version: 1` fields remain as commented declarations beside the runtime fields so the stable format is discoverable if later behavior needs them. Dictionary type `values` are the only heterogeneous schema numbers; their localized unmarshaler preserves exact number literals as `json.Number` without requiring the entire schema to use `json.Decoder.UseNumber`.

Classes are indexed by their signed 64-bit `class_uid`, and observable type captions are indexed when the schema is loaded. OCSF `integer_t` and `long_t` values are treated as signed 64-bit integers. Traversal-cache initialization resolves every attribute's final primitive type through dictionary type inheritance and builds immutable indexes from integral enum values to their existing schema definitions. The conventional numeric enum ID 99 has a dedicated pointer; among the remaining values, a contiguous set uses an offset-indexed slice, a sparse set of at most 16 definitions uses a sorted linear scan, and a larger sparse set uses an `int64` map so private schema extensions remain efficient without assuming OCSF's usual density. Type constraints and regular expressions are resolved when the corresponding values are validated.

`Schema` is a concrete public handle that owns an internal pipeline factory rather than wrapping a separate public state object. `Pipeline` is a public handle containing a pointer to the private processing engine. The public types own their documented APIs while their state and implementation remain internal. Ordinary caller code can use inferred variables without exposing internal schema or processor representations. Their zero values return initialization errors. Loaded `Schema` values are immutable and safe for concurrent use.

## Event Processor Construction

Callers pass functional options to `Schema.NewPipeline`, which resolves them into one immutable `PipelineConfig` and validates the result before constructing a `Pipeline`:

```go
pipeline, err := schema.NewPipeline(
	eventschema.WithEnumSiblings(enrichment.Add),
	eventschema.WithObservables(enrichment.Add),
	eventschema.WithValidation(),
)
```

`WithEnumSiblings` and `WithObservables` each take an `enrichment.Action` (`enrichment.None`, `enrichment.Add`, `enrichment.Remove`, or `enrichment.ForceRemove`) and configure one of the two independent mutation components. None leaves that component unchanged. Add enriches missing enum siblings or generates observables. Remove safely deletes only entries this pipeline can prove redundant, preserving values it cannot prove redundant. Force-remove deletes the entire `observables` attribute or supported enum siblings without per-entry caption analysis. Enum-sibling processing supports enums with same-shaped string siblings in scalar and array form. `WithObservables` optionally restricts observable generation to a nonempty set of schema-defined observable type IDs; pipeline construction validates and deduplicates that selection into an immutable set. The nil set means unrestricted generation and bypasses hash lookup in the default hot path. Class-observable tries omit excluded declarations when the pipeline is constructed; object, attribute, and dictionary-derived declarations use the same set during traversal.

`WithValidation` enables the validation processor and accepts nested `ValidationOption`s: `WithWarnOnMissingRecommended()` reports missing recommended attributes, and `WithValidationObservablePathNotation` selects the preferred observable path notation used in validation diagnostics. `WithSuppressValidation` selects codes independently of level and suppresses all suppressible findings when its code list is empty. The three class-resolution findings are mandatory because processing cannot continue without a resolved class; explicitly selecting one for suppression is invalid, while suppress-all retains it. Level policy options may still change the effective warning/error level of every code; their empty code lists select all codes at the level named by the option. Every explicit list selects exactly those codes regardless of current defaults. Selecting a code's current default is valid so the configuration continues to express its intent if that default changes. Incompatible actions for one selected code are rejected during pipeline construction. The resolved policy stores explicit code settings in an immutable sparse map; absence means no code-specific override. Empty-list policies use pipeline-level flags instead of filling that map, which also makes later-added codes inherit the requested all-suppressible, all-errors, or all-warnings behavior. An unconfigured pipeline retains a nil map and false flags.

`WithSuppressIssues` and `WithSuppressIssuesByStrings` configure per-pipeline issue suppression. Called with no codes, they suppress every tolerable issue; called with specific `issue.IssueCode` values, or with dynamically loaded name strings validated during pipeline construction, they suppress only those codes. Suppression is immutable pipeline state, applies independently to each mutating processor, and does not affect mutations, counters, validation findings, Go errors, or mandatory issues reporting incomplete processing, including class-resolution failure and the shared traversal limitation.

`eventschema.PipelineOption` and its nested option interfaces are intentionally sealed. They provide a small construction contract without exposing the internal configuration or visitor protocols. The internal engine accumulates a mutable field-based result during traversal. The public pipeline wraps those values in an opaque concrete `eventschema.ProcessingResult`, whose typed accessors return the canonical processor-specific structs owned by `eventresult`. This keeps mutation inside the hot internal path while allowing new processor-family accessors to be added without changing the public result representation. The result uses private value storage rather than an interface or pointer-backed handle. Compiler diagnostics confirm that the supported Go toolchain inlines every simple accessor across package boundaries, reducing calls to direct private-state access without interface boxing or an inherently necessary allocation. The abstraction is therefore zero-cost in current supported builds while retaining room for backward-compatible API growth.

`Schema.NewPipeline` is the authoritative validator for processing semantics. Construction returns an aggregate error containing every detected invalid or contradictory option: an unsupported action, a configuration with no enabled mutation or validation action, enrichment path notation or observable type IDs supplied without adding observables, issue suppression naming an unknown or mandatory code, and validation policy naming an unknown code or assigning conflicting actions to one code. The CLI additionally validates flag relationships so it can identify invalid flags directly; path, output, overwrite, and traversal rules remain CLI concerns.

Enum-sibling work is always built ahead of observable work, so enum siblings added, retained, or removed are visible (or already absent) when observables are generated or analyzed, and both mutation phases always run before validation, regardless of the order options were passed to `NewPipeline`. This ordering has no exception: an observable derived from an enum sibling that mutation has already removed cannot be verified and is retained, not removed. Mutating work is dispatched through a concrete internal union type rather than an interface; an equivalent interface-based version measurably adds one heap allocation per `ProcessEvent` call, confirmed by benchmark rather than by escape-analysis inference alone (see the `mutationDispatcher` comment in `internal/processing/pipeline.go` for the exact numbers and reproduction command). Validation is dispatched last. New mutating processors must preserve validation as the final phase.

Constructed `Pipeline` values contain immutable processor configuration and are safe for concurrent use when each call receives a distinct event map.

## Hot-Loop Performance

`Pipeline` is designed to be constructed once and reused while processing thousands or tens of thousands of events per second. `ProcessEvent`, its schema-guided traversal, and processor visitor callbacks are therefore hot-loop code.

Loaded schema data, ordered processors, processor configuration, compiled constraints, and other reusable data belong to the immutable schema or pipeline rather than the per-event processing context. Ordered attribute and constraint names, resolved primitive types, and numeric enum indexes are initialized once beside their class or object definitions. Schema initialization rejects cyclic dictionary type inheritance because such a type cannot resolve to meaningful event-processing behavior. Validation-enabled pipelines additionally initialize an immutable `internal/validationcache.Cache` containing the parsed schema version, compiled type regular expressions, resolved range and maximum-length constraints, and allowed values normalized to their OCSF primitive types; cache construction repeats the cycle defense for internally constructed compiled schemas that bypass normal loading. `internal/validationcache` owns both cache construction and its concurrency-safe lazy lifecycle; enrichment-only pipelines do not pay that cost. A processing context contains only mutable state for one event plus references to shared immutable data. Processing must not copy processor collections, rebuild reusable traversal data, or perform other avoidable per-event work merely to recover information already owned by the pipeline.

Compiled schemas are expected to come from `ocsf-schema-compiler`, which owns semantic schema validation, including reference integrity. The toolkit does not duplicate that validation pass. Schema loading retains only checks needed to recognize supported compiled formats, construct internal indexes safely, and fail defensively instead of panicking when input is malformed or corrupted. These structural checks reject null class, object, attribute, and dictionary-type definitions and malformed observable type enum IDs rather than silently omitting them from processing.

Schema traversal metadata is initialized before event processing, and first-use processor-cache initialization occurs only while constructing a pipeline. `ProcessEvent` reads immutable shared schema data and the already initialized validation cache without acquiring cache locks. Event-local analysis stays in the processing context. New shared caches for event-controlled values must be bounded, concurrency-safe, and benchmarked against uncached processing; a cache should not be added when lookup, synchronization, or miss churn costs more than allocation-free computation.

Implementations should avoid unnecessary heap allocations and temporary maps, slices, strings, reflection, parsing, sorting, and conversion in the traversal path. Pipeline-owned issue suppression is checked before constructing issue diagnostics; its zero value adds no map lookup to the default collect-all path, while selected suppression uses an immutable code set. Validation policy is decided before formatting a validation message, although validation call sites may prepare small detail maps before that decision. Processing issues, validation warnings and errors, and returned Go errors must not repeat event values in messages or details; exact event paths and safe schema context provide diagnostic strength without duplicating potentially sensitive content into natural logging inputs. Result messages preserve graphic Unicode but render control characters, non-graphic Unicode, and invalid UTF-8 bytes as visible escape sequences so schema-controlled text cannot alter log structure or terminal presentation. Collections included for other diagnostic context must not expose mutable event-, schema-, or pipeline-owned storage. This is a design constraint, not permission for speculative complexity: use representative benchmarks, allocation counts, escape analysis, and profiles to identify meaningful costs. Performance changes must preserve correctness, deterministic diagnostics, concurrency safety, malformed-input handling, and the public processing contract.

Ordinary tests enforce conservative allocation ceilings for representative processor combinations. Runtime, bytes-per-operation, and schema/pipeline construction costs are evaluated by running the benchmark suite against the newest reachable release tag on the same machine and comparing statistically with `benchstat`. Prerelease tags currently participate in the single newest-release baseline. If prereleases later become part of the final release strategy, baseline selection should separately report the newest prerelease and newest stable release.

## Single-Pass Visitor

Each `ProcessEvent` call creates a fresh stack-resident `processContext` and performs one recursive schema-guided walk. Concrete internal processors receive hooks for the resolved class, objects, ordinary attributes, enum sibling pairs, completed classes and objects, and the completed event; dispatch to those hooks uses a concrete union type rather than an interface, which avoids the one heap allocation per event that an interface-based equivalent measurably introduces (see "Event Processor Construction" above).

The shared walker owns traversal, profile filtering, object lookup, array handling, recursion boundaries, and path tracking. Its immutable traversal cache pairs each ordered attribute name with its definition, resolves object-definition references and final primitive types, builds integral enum indexes, and links supported enum attributes with their string siblings in both directions during schema initialization, avoiding repeated schema-map lookups and type-ancestry scans. A supported source has direct type `integer_t` or `long_t`; its target exists, is not an enum, has direct type `string_t`, and has the same scalar or array shape. Initialization ignores invalid relationships and reports the specific source or target condition, while a `sibling` declaration on a non-enum is irrelevant and silent. Schema loading still rejects two otherwise-supported enum relationships that assign the same target. Profiles activate the enum and sibling definitions independently. When both definitions are active, the enum's ordered schema entry owns the pair dispatch and the sibling's entry is skipped, so one callback receives both definitions regardless of which event values are present. When only one definition is active, the walker dispatches it as an ordinary attribute and does not perform pair-specific work through the inactive definition. Active event profiles are read directly into an event-local set without first constructing an intermediate profile-name slice. The walker excludes inactive profile-scoped definitions from mutation dispatch without constructing a filtered map, but sends present inactive attributes to a validation-only hook. It also enumerates event keys after each closed item to send attributes absent from the compiled definition to a separate validation-only hook. Validation performs a bounded shallow check for an inactive attribute: complete primitive-scalar validation, underlying primitive validation for an enum, array-shape validation without elements, or object-shape and resolved-type validation without contents. Detected errors become an `invalid_value` validation result nested in the profile finding. The validation cache similarly groups each dictionary type's resolved primitive type and constraints into one immutable record, so validation performs one type lookup per value. Numeric enum lookup uses an integer-spelled `json.Number` directly against the existing schema string map when the schema keys are canonical; integral Go values and normalized floating-point representations use the numeric index. The first numeric `json.Number` in an event records whether that event uses decimal or exponent syntax so later lookups avoid a predictably unsuccessful string-map probe, while every miss still takes the checked normalization path and mixed encodings remain correct. The `internal/eventpath` stack uses inline storage for ordinary nesting and records attribute and array-index elements without eagerly concatenating strings. Processors render the current logical path only when they need an indexed diagnostic path, an index-free schema path, or a generated observable name in a configured `pathstyle.Style`. Diagnostic child, sibling, and array paths remain structural until rendering rather than being assembled or parsed as strings. When observable addition is enabled, the enrichment processor compiles class-specific dotted observable declarations into immutable per-class tries during pipeline construction. Enrichment matches the walker path structurally against the selected trie while ignoring array-index elements; pipelines that do not add observables and schemas without class-specific declarations retain no trie. Individual processors perform processor-specific work:

- Enrichment adds missing enum siblings, gathers schema-defined observables, and writes generated observables at the end of the event.
- Enrichment removal removes supported enum siblings through pair callbacks during traversal, then analyzes or removes observables after class traversal. This ensures observable work and validation observe the final sibling state.
- Validation checks requirements, unknown attributes, types, enum values and siblings, deprecations, constraints, schema version, `type_uid`, profiles, and observable references.

A visitor can inspect more deeply when its behavior requires it, but traversal remains centralized. This avoids separate full enrichment and validation walks while keeping their logic in separate source files.

Recursive OCSF object relationships are bounded by scanning the active path for a prior occurrence of the current object attribute name, ignoring array-index elements. The walker encounters the repeated attribute and reports its path, then does not deliver an object callback or traverse any attribute inside that object. This allocation-free, branch-local guard relies on the OCSF attribute dictionary's consistent relationship names, permits useful recursion through differently named relationships, and applies the same boundary to every processor. It prevents traversal from following the potentially geometric expansion created by recursive object arrays or multiple recursive branches, protecting processing performance and robustness without imposing a general event-size or breadth limit. The repeated object value and its contents remain in the event but are outside schema-guided enrichment, removal, and validation. The first boundary reached produces one top-level `issue_event_traversal_limited` processing issue for the event; it is an implementation limitation rather than a validation finding and cannot be suppressed.

`internal/observablepath` owns the observable-name path language and path resolution mechanics. It parses bare, `[]`, `[*]`, numeric index, and `$`-rooted paths and checks references and preferred notation against the active compiled class. Schema reference checks apply the same repeated-attribute boundary as the event walker. Runtime resolution uses iterative, cycle-aware array traversal and answers the object, null, or scalar-string match requested by its consumer without materializing a flattened value collection. `internal/observable` owns entry analysis, schema-based observable discovery, semantic duplicate identity, representation-preserving append and filter operations, and diagnostics derived from typed failure classifications. It resolves observable paths against actual event content, compares scalar values after the toolkit's stable scalar-to-string formatting, and distinguishes value-bearing scalar observables from valueless object observables. An explicit null observable value matches either an explicit null or a missing branch at its schema-valid event path, reflecting OCSF's equivalence of null and missing values. `internal/processing` retains processor timing, mutation policy, counters, and selection of processing issues versus validation findings: enrichment removal analyzes before mutation to decide which entries are redundant, while validation analyzes the final event using its final observable indexes.

An attribute used directly with `object_type: "object"` is the OCSF convention for an open-ended JSON-like object, so unknown nested keys are allowed. All event classes and concrete object types remain closed against their active compiled attributes, including when profile filtering leaves no active attributes. A concrete object may still gain inherited attributes when their profiles are active because the compiler flattens those profile annotations onto the derived object.

Mutating processors use a shared internal diagnostic representation when malformed event content prevents requested work. Each processor maps that diagnostic into an `eventresult.ProcessingIssue` with a typed `issue.Source`; validation separately maps retained invalid content into validation errors or warnings. Class-resolution failure and a shared traversal limitation instead produce `processing` source issues regardless of which processors are configured. Enrichment diagnostics are intentionally narrow: they cover enum siblings or observables that could not be added, enum ID 99 siblings synthesized from the schema caption, and generated observable duplicates that were skipped, while unrelated event validity remains the validator's responsibility. Generated observables preserve existing entries and append in traversal order after semantic duplicate suppression. The processing context records the first index and notation of this generated suffix. Same-operation validation analyzes the existing prefix and may skip redundant semantic resolution of the trusted suffix, while still checking preferred notation when the configured styles differ. Separate enrichment-then-validation tests verify that generated entries satisfy the full validation contract without using this shortcut. Duplicate identity uses the exact observable name, an integral-equivalent type ID, and the distinction among an omitted, null, or exact string value; derived type captions and unrelated fields are ignored. After class resolution succeeds, observable enrichment and removal delete the `observables` attribute when their work leaves it as an empty array.

If `class_uid` is missing, has the wrong type, or does not identify a compiled class, the processing context records a mandatory processing issue and stops before any mutation, class-scoped traversal, or completed-event callback. This includes force removal even though that operation could mechanically run without class data; class resolution is the pipeline's minimal OCSF-event sanity check. Validation additionally records a dedicated, non-suppressible finding when enabled. Validation policy may change that finding's effective level because level and suppressibility are separate concerns. Recoverable validation failures after class resolution are accumulated rather than stopping processing.

## Mutation And Results

`ProcessEvent` mutates its `jsonish.Map` argument in place when enrichment or another mutating processor is enabled. Processing is not transactional. If it returns a Go error, the map may already be partially modified; callers that need the original event must deep-copy it first.

OCSF object attributes with an explicit null value are treated as missing throughout validation, enrichment, and enrichment removal. This applies to requirements, constraints, unknown-attribute checks, enum siblings, and the top-level `observables` attribute. A null array element is not missing and fails validation because no OCSF array element type permits null. Observable entries are the format-driven exception: an omitted `value` denotes an object observable, while an explicit null `value` denotes a scalar observable referring to null or missing event content.

OCSF validation findings are returned by `eventschema.ProcessingResult.Validation()`, not as Go errors. `ProcessingResult` is an opaque concrete value with private value storage and typed accessor methods, allowing future processor families to add results without changing its public representation or introducing interface dispatch in the event-processing path. Each validation finding has a severity-neutral stable machine-readable code, an explicit effective level, a human-readable message, and code-specific structured details. `validation.Code.DefaultLevel()` reports the toolkit's default policy independently of the finding's effective level, while `validation.Code.Suppressible()` distinguishes mandatory class-resolution findings. A Go error means the processor could not operate on the supplied input. Non-fatal processing diagnostics, including class-resolution failures and shared traversal limitations, are returned separately by `ProcessingResult.Issues()`, while `SuppressedIssueCount()` accounts for otherwise-reportable issues omitted by policy.

The event map and its nested maps and slices must not be accessed concurrently during processing. Separate events may be processed concurrently by the same processor.

## Numeric Values

Validation accepts normal Go numeric values from non-JSON sources. Numeric conversion is based on value compatibility rather than encoding-specific representation: integral fields accept finite, in-range, mathematically integral floating-point representations, while floating-point fields accept compatible integral representations. For JSON, `json.Number` is preferred because decoding directly to `float64` can lose integer precision. The `jsonio` package enables `json.Decoder.UseNumber()` for this reason.

Array attributes accept JSON-native `[]any` values as well as typed Go slices and fixed arrays from programmatic and non-JSON event sources. Defined container types are traversed like their unnamed equivalents. Every element undergoes the same schema validation regardless of its container representation, so an unsupported homogeneous element produces the same wrong-type finding as that value in `[]any`. Common concrete slice types retain their fast paths, while defined containers and fixed arrays require reflection because a runtime type switch cannot match them as their underlying unnamed slice or every possible array length.

Integral validation rejects non-integral values and applies signed 64-bit bounds where required. Numeric range constraints are inclusive.

## CLI Boundary

`cmd/ocsf-toolkit` owns filesystem and command-line concerns: selecting input files, mapping output trees, preventing unintended overwrites, summary formatting, and exit codes. These policies do not belong in the event-processing library. Input event files are never modified.

The CLI uses a flag-based design because enrichment, enrichment removal, and validation are independent processing actions that may be combined in one invocation. Modeling them as top-level subcommands would make those actions mutually exclusive or require an artificial command hierarchy. The CLI therefore uses pflag for POSIX/GNU-style option parsing and retains a small custom help formatter for its processing-oriented option groups.

The CLI mutation flags map directly to the independent `enum-siblings` and `observables` components used by the event-processing API. `--enum-siblings[=ACTION]` and `--observables[=ACTION]` set one component's action directly, where `ACTION` is `add`, `remove`, or `force-remove`. `--enrich`, `--unenrich`, and `--force-remove` are shorthand that set both components at once; they cannot be combined with each other or with the per-component flags, so different components may use different actions only through `--enum-siblings`/`--observables`.

The CLI validation policy flags map directly to the three nested library options. Bare `--suppress-validations` selects every suppressible finding; a bare level-change flag selects all codes at the named toolkit default level. An assigned comma-separated value selects explicit codes for any policy flag, with mandatory class-resolution codes rejected only for suppression. `--list-validation-codes` exposes each stable code, description, default level, and mandatory status without requiring a schema. Validation-error exit policy is evaluated from effective finding levels after suppression and remapping.

All directory-mode outputs share one `--output-dir` root with fixed `events/` and `reports/` namespaces. Both preserve input-relative directories; report filenames insert `.report` before the input filename extension. Every processing action produces a report so enrichment issues are not discarded. Each report aggregates the selected processor results for one source event and records `event_source` plus `event_destination` when a processed event was written. Single-event mode may instead select explicit event and report files and never chooses implicit destinations, including when stdin is the event source. This prevents event/report filename collisions without multiplying directory controls as processors are added.

Before processing begins, the CLI resolves and validates command-wide input and output roots plus explicit single-event destinations. This preflight validation checks the paths known at that time for output collisions and input/output overlap. The selected `--events-dir` must exist as an actual directory rather than a symbolic link. Directory processing then streams files directly from `filepath.WalkDir`; it does not retain a full list of event paths or calculated destinations, and it does not follow symbolic links found within the input tree. The first walk callback identifies the root without comparing its path on every later callback. If the root is no longer a directory when the walk begins, traversal intentionally processes no events, preserving the same successful result as an empty directory under that post-preflight race. Output paths are derived from each safe input-relative path beneath the fixed output namespaces.

Input and output directory trees must be disjoint after resolving symbolic links through each path's longest existing prefix, including when the selected output directory does not exist yet. Explicit paths receive a best-effort preflight comparison using platform path semantics and any filesystem identity already observable; a detected collision leaves the outputs unwritten. For explicit single-event file outputs, event and report identity is checked again after the event write and before the report write; a collision first observable at this stage leaves the completed event in place and suppresses the report. The selected output root itself may be a symlink because the user chose it explicitly, but existing output namespaces may contain only regular files and actual directories; symbolic links, Windows junctions, and other special filesystem entries are rejected. Without `--overwrite`, a directory-mode output root must be nonexistent or empty. Output is staged in a temporary file and installed by rename or hard link when the filesystem supports it. A filesystem without hard-link support uses an exclusive-create copy fallback that preserves the no-overwrite guarantee but cannot make the completed file visible atomically. Replacement fails unless `--overwrite` is selected. With `--overwrite`, files selected as output destinations are replaced without inspecting their prior contents; the staged file adopts an existing destination's permission bits immediately before replacement. Permission preservation and directory-derived collision and overlap protection after preflight validation are best effort because concurrent filesystem changes or distinct spellings that the filesystem treats as the same path may not be detected.

The CLI may process one file or walk a directory tree, but each JSON object is still passed independently to `ProcessEvent`. Directory outputs preserve paths that `filepath.IsLocal` identifies as safe after lexical cleaning. For a single input, cleaned paths accepted by `filepath.IsLocal` are preserved beneath the output namespace; this guarantees that joining the path to the namespace cannot escape it. An absolute, rooted, drive-relative, reserved, or otherwise non-local path is reduced to a safe filename so it cannot escape the output namespace or select a special device.

One invocation may select stdout for at most one output option: processed event, processing report, human-readable summary, or JSON summary. This keeps stdout a single output representation rather than a heterogeneous stream whose records require positional interpretation. `--pretty-json` applies to every JSON destination.

Summaries apply only to successfully completed directory processing. A human-readable summary is written to stdout by default and may be suppressed with `--quiet`. Explicit human-readable and JSON summary destinations are additive and may be selected together with or without `--quiet`, subject to the command-wide single-stdout-output rule. Human summaries reuse the CLI help renderer for consistent indentation and terminal-width-aware wrapping. JSON event reports and directory summaries carry independent integer `report_version` and `summary_version` fields, both currently 1. Summary aggregates and per-file entries use optional processor-shaped sections plus initialization, issue, and output accounting. After a fatal directory-processing error, the CLI stops without writing normal summaries and reports only the failure diagnostics and the number of event files processed before the error. stderr is reserved for errors, failure diagnostics, and nonfatal schema initialization issues.

All mutations and validation complete before event and report output is written. Processing reports retain the results of every selected processor, including when validation finds errors.

## Design Invariants

- Validation remains the final event-processing phase.
- Event mutation remains in-place and non-transactional unless the public contract is deliberately changed.
- OCSF integer types use signed 64-bit semantics.
- `jsonish.Map` remains the public JSON-object type.
- Validation findings remain data; only processing failures become Go errors.
- Event processing remains suitable for hot-loop use: reusable data is immutable and pipeline-owned, while per-event state and allocations are kept proportionate to the requested work and returned results.
- Filesystem overwrite and output-path policy remain in the CLI layer.
